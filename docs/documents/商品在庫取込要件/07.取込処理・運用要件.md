# 取込処理・運用要件

- 文書状態：確定版
- 更新日：2026年8月27日
- 対象システム：商品在庫管理システム

本書は、商品在庫取込の処理順序と、取込頻度および在庫基準日の運用要件を定める。  
取込元ごとの入力ファイルおよび検証の要件は[02.BOSS各在庫数レポート取込要件](02.BOSS各在庫数レポート取込要件.md)、[03.Amazon出品詳細レポート取込要件](03.Amazon出品詳細レポート取込要件.md)および[04.Amazon FBA在庫レポート取込要件](04.AmazonFBA在庫レポート取込要件.md)に、保存結果は[05.商品在庫保存データ](05.商品在庫保存データ.md)に定める。

## 1. 取込処理の流れ

取込処理は次の順序で実行する。

1. ファイルを選択し、在庫基準日を指定する。
2. ファイル種別、文字コード、区切り文字を判定する。
3. 列名の前後空白を除去する。内部の空白は除去しない。
4. 必須列の存在を確認する。
5. 取込対象外の行を除外する。出品詳細レポートは`数量`が空欄の行、FBA在庫レポートは`Warehouse-Condition-code`が`SELLABLE`以外の行を、以降の行検証および登録・更新の対象から除外する。
6. 各行の形式を検証する。
7. 倉庫区分、数量を標準形式へ変換する。
8. システム内商品コードを解決する。BOSSは`SKUコード`をそのまま採用し、未登録のSKUをSKUマスタへ自動登録する。Amazonは商品コード対応表を参照し、未対応の行を除外する。
9. 一意キーによる重複判定を行い、取込対象行を確定する。
10. BOSSは商品単位の整合性を検証し、登録・更新しない商品を特定する（[BOSS各在庫数レポート取込要件 第8.2節](02.BOSS各在庫数レポート取込要件.md)）。
11. 取得区分が`手入力`の既存レコードを特定し、上書き対象から除外する。
12. 在庫基準および在庫取込を登録または更新する。
13. 在庫数を追加または更新する。
14. 直前の同一倉庫区分の取込に存在し、今回のファイルに存在しないSKUを消失件数として特定する。
15. 取込件数、更新件数、除外件数、未対応商品件数、消失件数、警告件数、エラー件数を記録する。
16. 同一在庫基準日の全取込元の取込が完了している場合は、倉庫横断の検証を行う（第3章）。
17. エラー・警告内容を利用者が確認できるようにする。

在庫数は上書きせず在庫基準日ごとに蓄積する。過去の在庫基準日のレコードは、本処理のいずれの段階でも更新・削除しない（[商品在庫保存データ 第7章](05.商品在庫保存データ.md)）。

## 2. 取込頻度・在庫基準日

在庫の取込は月1回とする。実行担当者は、原則として本業務の担当者とする。  
販売実績の取込が出勤日の毎朝1回であるのに対し（[販売実績取込要件の取込処理・運用要件 第2章](../販売実績取込要件/05.取込処理・運用要件.md)）、在庫は月1回である。両者の取込頻度が異なることを前提に、在庫の鮮度を扱う（[在庫利用要件 第6章](06.在庫利用要件.md)）。

在庫基準日の指定は次のとおりとする。

- 在庫基準日は取込時に必ず指定する。省略を許可しない。
- 在庫基準日には、レポートを出力した日を指定する。在庫はその時点の残高を表すスナップショットであり、出力日と異なる日の在庫を再現できないためである。
- 同一の取込回では、3つの取込元すべてに同じ在庫基準日を指定する。
- 未来日を指定できない。
- 過去日の指定は、取込漏れの遡及登録のために許可する。ただし、当該日に出力したレポートを取り込む場合に限る。指定した日とファイルの出力時点が一致しているかはシステムでは検証できないため、運用によって担保する。
- 既に在庫数が登録済みの在庫基準日を指定した場合は、再取込として扱う（[商品在庫保存データ 第7章](05.商品在庫保存データ.md)）。

取込を実施する日は、月次の在庫確認および発注判断の業務サイクルに合わせて定める。具体的な実施日は未確定である。

## 3. 取込順序と倉庫横断の検証

3つの取込元の取込順序は問わない。取込元ごとに独立して処理し、他の取込元の取込結果に依存する判定を行わない。

ただし次の検証は、単独のファイルでは判定できないため、同一在庫基準日の全取込元の取込が完了した時点で行う。

- 出品詳細レポートで`数量`が空欄であり、かつFBA在庫レポートにも存在しないSKUの検出（[Amazon出品詳細レポート取込要件 第3.2節](03.Amazon出品詳細レポート取込要件.md)）。
- 同一の在庫基準日に4つの倉庫区分すべての在庫が揃っているかの確認。

全取込元の取込が正常完了した時点で、在庫基準の取込状態を`完了`とする。  
`完了`に至らない在庫基準日についても、正常完了した取込元の在庫は在庫試算で使用できる。在庫試算は倉庫区分ごとに最新のレコードを独立して採用する（[商品在庫保存データ 第8章](05.商品在庫保存データ.md)）。

## 4. 初回取込

初回取込では、次を実施する。

- 初回の在庫基準日について、3つの取込元すべてのレポートを取得して取り込む。
- 在庫は過去の残高を遡って取得できないため、販売実績のような過去分の一括登録は行わない（[販売実績取込要件の取込処理・運用要件 第2.1節](../販売実績取込要件/05.取込処理・運用要件.md)）。在庫の蓄積は初回取込以降とする。
- 初回取込の在庫基準日より前の日付を基準日とする在庫試算は実行できない。

## 5. マスタ整備の前提

Amazonの2つのレポートは、商品コード対応表に登録されたSKUだけを在庫として登録できる（[商品在庫取込要件 第5.4節](01.商品在庫取込要件.md)）。実データでは、FBA在庫レポートの1327件のうちBOSSの`SKUコード`と完全一致するものが43件にとどまる。対応表が未整備のままでは、Amazon側の在庫はほとんど登録されない。

このため、初回取込の前に次を実施する。

- 商品マスタは、商品マスタ登録基準を満たす品番とその所属SKUだけを手動で整備する。全SKUの商品属性を登録しない（[販売実績取込要件 第5.3節](../販売実績取込要件/01.販売実績取込要件.md)）。
- 対応表は販売実績と共通であるため、販売実績取込のために整備した対応表を流用できる。ただし販売実績に現れないSKUは対応表に登録されていないため、在庫取込のために追加登録する。
- 未対応商品として記録されたSKUは、対応表の登録後に同一の在庫基準日で再取込する。

対応表の整備状況を確認できるよう、直近の取込における未対応商品件数を表示する。

## 6. 在庫取込の運用上の制約

- BOSS各在庫数レポート、Amazon出品詳細レポート、Amazon FBA在庫レポートは、それぞれ別の画面から出力する。出力時点が離れるほど、同一在庫基準日として扱う3ファイルの間に時点のずれが生じる。同日中に出力することを運用の前提とする。
- 出力から取込までの間に在庫が変動しても、取り込んだ在庫はレポート出力時点の値である。取込日時ではなく在庫基準日を在庫の時点として扱う。
- レポートの出力に失敗した取込元がある場合も、取得できた取込元だけを先に取り込んでよい。残りは同じ在庫基準日を指定して後から取り込む。
