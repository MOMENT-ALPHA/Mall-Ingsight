# 商品在庫保存データ

- 文書状態：確定版
- 更新日：2026年8月27日
- 対象システム：商品在庫管理システム

本書は、取込対象となった在庫を保存する全倉庫共通の形式および保存項目を定める。  
取込元ごとの取得元と変換規則は[02.BOSS各在庫数レポート取込要件](02.BOSS各在庫数レポート取込要件.md)、[03.Amazon出品詳細レポート取込要件](03.Amazon出品詳細レポート取込要件.md)および[04.Amazon FBA在庫レポート取込要件](04.AmazonFBA在庫レポート取込要件.md)に、全取込元に共通する方針は[01.商品在庫取込要件](01.商品在庫取込要件.md)に定める。

取込対象となったデータは、入力ファイルの列構成のまま保存せず、全倉庫共通の形式へ変換して保存する。  
在庫の正本は`在庫数`とし、取込処理の証跡は`取込履歴`と`取込指摘`に保存する。  
入力ファイルの全列を複製したデータは保持せず、本書に定義する項目以外、取込判定専用項目および商品名等のマスタ側で管理する項目は保存しない。

## 1. データ構成

| 保存データ | 1レコードの単位 | 主な関係 |
|---|---|---|
| 在庫基準 | 1つの在庫基準日 | 複数の在庫取込を持つ |
| 在庫取込 | 在庫基準日と取込元の組合せ | 1件の在庫基準に属し、複数の在庫数を持つ |
| 在庫数 | 在庫基準日、倉庫区分およびSKUの組合せ | 1件の在庫取込に属する。手入力の場合は属さない |
| 倉庫マスタ | 1つの倉庫区分 | 在庫数から参照される |
| 取込履歴 | 1回のファイル取込 | 在庫取込の最終更新元になる |
| 取込指摘 | 1回の取込で検出した警告またはエラー1件 | 取込履歴に属し、該当する倉庫区分・SKU・元ファイル行を特定する |

```text
在庫基準 1 ── N 在庫取込 1 ── N 在庫数 ── 参照 ── 倉庫マスタ
                  │                 │
                  └── 最終更新元 ────┘
                          │
              取込履歴 1 ── N 取込指摘
```

在庫数は、SKUマスタのSKUおよび[商品在庫取込要件 第5章](01.商品在庫取込要件.md)の商品コード対応表を参照する。いずれも販売実績と共通のマスタであり、在庫のために別途保持しない。

### 1.1 保存形式の選択

在庫を保持する構造には、次の2つの形式が考えられる。

| 形式 | 1レコードの単位 | 在庫数量の持ち方 |
|---|---|---|
| 行分割形式 | 在庫基準日、倉庫区分およびSKUの組合せ | 1レコードに1倉庫区分の販売可能在庫を持つ |
| 列展開形式 | 在庫基準日およびSKUの組合せ | 1レコードに4倉庫区分の販売可能在庫を列として持つ |

本システムでは行分割形式を採用する。理由は次のとおりである。

- **取込単位と保存単位が一致する。** 4つの倉庫区分は3つの取込元から別々のファイルとして取り込まれる。行を分けることで、倉庫区分ごとに取込元、取込日時、取得区分および取込履歴を持てる。列展開形式では1レコードが3回の取込によって部分的に更新されるため、どの値がどの取込に由来するかをレコード単位では表せず、[要件定義書 FR-050](../要件定義書.md)が求める在庫の取得元・取得日時・取得区分の保持には、これらの項目を4倉庫区分分だけ列として持つ必要がある。
- **倉庫区分ごとに独立した在庫基準日を扱える。** 在庫試算は倉庫区分ごとに最新の在庫基準日を独立して採用する（第8章）。列展開形式では、1つのSKUについて列ごとに異なる在庫基準日のレコードを参照することになる。
- **未取得と在庫0を区別できる。** 当該倉庫区分の在庫が0であることと、当該倉庫区分の在庫をまだ取得できていないことを、レコードの有無で区別できる。
- **倉庫の追加時に保存データの定義を変更せずに済む。** 倉庫区分は本要件の設計過程でも3区分から4区分へ変更されており、今後も追加されうる。

SKU1行に対して倉庫別の在庫数を横並びに表示する形式は、画面および出力の表示形式として第9章に定める。保存形式としては採用しない。

### 1.2 レコード件数の試算

行分割形式は列展開形式の4倍のレコード件数となる。件数が保存形式の制約になるかを確認するため、BOSS各在庫数レポートの実データのSKU数1530件および倉庫区分4区分を前提として試算した。

| 取込頻度 | 形式 | 1在庫基準日あたり | 年間 | 5年間 |
|---|---|---|---|---|
| 月1回（初期の運用） | 行分割形式 | 6,120件 | 73,440件 | 367,200件 |
| 月1回（初期の運用） | 列展開形式 | 1,530件 | 18,360件 | 91,800件 |
| 日次（将来の拡張時） | 行分割形式 | 6,120件 | 2,233,800件 | 11,169,000件 |
| 日次（将来の拡張時） | 列展開形式 | 1,530件 | 558,450件 | 2,792,250件 |

試算結果は次のとおりである。

- 初期の運用である月1回の取込では、[要件定義書 第10.2節](../要件定義書.md)が求める5年分の保持でも約37万件であり、件数として大きくない。
- 取込頻度を日次へ引き上げた場合でも年間約223万件であり、販売実績の注文明細と同程度の規模である。
- SKU数が1万件へ増加した場合でも、月1回の取込では年間48万件である。

いずれの条件でも件数が性能上の制約にならないため、レコード件数を保存形式の判断材料とせず、第1.1節の理由により行分割形式を採用する。

同じ前提で試算した販売実績の件数は、5年保持時点で販売注文と販売注文明細の合計が約43万件であり、在庫の約37万件と同程度である（[販売実績保存データ 第1.1節](../販売実績取込要件/04.販売実績保存データ.md)）。ただし件数の増え方は両者で異なる。在庫は取込のたびにその時点の残高を追加登録するため取込頻度に比例して増えるが、販売実績は再取込が既存レコードの更新であるため販売数量にだけ比例する。

将来、件数が問題となった場合も、保存形式の変更ではなく保持年数の制限で対応する。在庫試算および画面表示が使用するのは倉庫区分ごとの最新の在庫基準日のレコードであり（第8章）、それ以前の在庫基準日のレコードは推移の確認と監査のために参照するだけである。保持年数の設定は[要件定義書 第10.2節](../要件定義書.md)のデータ保持方針に従う。

## 2. 共通の保存規則

- 内部IDはシステムが付与し、取込元のSKUや商品IDとは分けて保持する。内部IDの物理的な型は詳細設計で決定する。
- 取込元が付与するSKUおよび商品IDは、先頭の0や桁数を失わないよう文字列として保存する。英字の大小および内部の空白を保持する（[商品在庫取込要件 第5.3節](01.商品在庫取込要件.md)）。
- 在庫基準日は日付として保存する。時刻を持たせない。
- 在庫数量は整数で保存する。負値を許容し、取込時に0へ補正しない。
- 作成日時、更新日時および最終取込履歴IDを在庫数に保存する。
- 在庫数は物理削除しない。過去の在庫基準日のレコードを更新しない。
- 取込元によって値が存在したりしなかったりする保存項目を設けない。取込元に対応する列がない場合も、代替の取得元または定数を取込元ごとに定める。この規則は[販売実績保存データ 第2章](../販売実績取込要件/04.販売実績保存データ.md)と共通である。

保存する在庫数量は販売可能在庫の1項目だけとする。実在庫数および引当済数は保存しない（[商品在庫取込要件 第4.5節](01.商品在庫取込要件.md)）。取込元によって取得できたりできなかったりする数量項目を保存しないことで、上記の規則を満たす。

| 保存項目 | BOSS各在庫数レポート | Amazon出品詳細レポート | Amazon FBA在庫レポート |
|---|---|---|---|
| 販売可能在庫 | `実在庫 (倉庫毎)` − `引当済 (倉庫毎)` | `数量` | `Quantity Available` |
| 取込元商品ID | `商品ID` | `ASIN 1` | `asin` |

## 3. 在庫基準

在庫基準は、1つの在庫基準日について、どの取込元の在庫が揃っているかを表す。一意制約は`在庫基準日`とする。

| 保存項目 | 内容 | 必須 |
|---|---|---|
| 在庫基準ID | システムが付与する内部ID | 必須 |
| 在庫基準日 | 在庫が成立した日。担当者が取込時に指定する | 必須 |
| 取込状態 | `取込中`または`完了`。全取込元の取込が正常完了した時点で`完了`とする | 必須 |
| 完了日時 | `完了`となった日時 | 状態が`完了`の場合は必須 |
| 作成日時 | 初回登録日時 | 必須 |
| 更新日時 | 最終更新日時 | 必須 |

在庫基準は、最初の在庫取込を登録した時点で自動的に作成する。担当者が個別に作成しない。

## 4. 在庫取込

在庫取込は、1つの在庫基準日における1取込元の取込を表す。一意制約は`在庫基準日 + 取込元`とする。

| 保存項目 | 内容 | 必須 |
|---|---|---|
| 在庫取込ID | システムが付与する内部ID | 必須 |
| 在庫基準ID | 所属する在庫基準の内部ID | 必須 |
| 取込元 | `BOSS各在庫数レポート`、`Amazon出品詳細レポート`または`Amazon FBA在庫レポート` | 必須 |
| 対象倉庫区分 | 当該取込元が在庫を供給する倉庫区分。BOSSは`BOSS自社倉庫`と`RFC`の2つ | 必須 |
| 最終取込履歴ID | この在庫取込を最後に登録・更新した取込 | 必須 |
| 取込結果 | 当該取込元の処理結果 | 必須 |
| 作成日時 | 初回登録日時 | 必須 |
| 更新日時 | 最終更新日時 | 必須 |

同一の在庫基準日および取込元を再取込した場合は、在庫取込を新規作成せず、最終取込履歴IDと更新日時を今回の取込に変更する。取込履歴は再取込のたびに追加する（第10章）。

## 5. 在庫数

在庫の正本である。一意制約は`在庫基準日 + 倉庫区分 + システム内商品コード`とする。再取込時はこの組み合わせで既存レコードを特定して更新する。

| 保存項目 | 内容 | BOSS各在庫数レポート | Amazon出品詳細レポート | Amazon FBA在庫レポート | 必須 |
|---|---|---|---|---|---|
| 在庫数ID | システムが付与する内部ID | 自動付与 | 自動付与 | 自動付与 | 必須 |
| 在庫基準日 | 在庫が成立した日 | 取込時に指定 | 取込時に指定 | 取込時に指定 | 必須 |
| 倉庫区分 | `BOSS自社倉庫`、`RFC`、`Amazon自社倉庫`または`FBA` | `倉庫`を変換 | `Amazon自社倉庫`固定 | `FBA`固定 | 必須 |
| システム内商品コード | BOSSの`SKUコード`と同一の商品コード | `SKUコード`をそのまま採用 | 対応表から取得 | 対応表から取得 | 必須 |
| 取込元SKU | 取込元が保持するSKU | `SKUコード` | `出品者SKU` | `seller-sku` | 自動取込では必須 |
| 取込元商品ID | 取込元の商品識別子 | `商品ID` | `ASIN 1` | `asin` | 自動取込では必須 |
| 販売可能在庫 | 当該倉庫から出荷に充てられる数量 | `実在庫 (倉庫毎)` − `引当済 (倉庫毎)` | `数量` | `Quantity Available` | 必須 |
| 取得区分 | `自動取込`または`手入力` | `自動取込` | `自動取込` | `自動取込` | 必須 |
| 在庫取込ID | 所属する在庫取込 | 在庫取込から特定 | 在庫取込から特定 | 在庫取込から特定 | 取得区分が`自動取込`の場合は必須 |
| 最終取込履歴ID | このレコードを最後に登録・更新した取込 | 取込履歴ID | 取込履歴ID | 取込履歴ID | 取得区分が`自動取込`の場合は必須 |
| 作成日時 | 初回登録日時 | 自動付与 | 自動付与 | 自動付与 | 必須 |
| 更新日時 | 最終更新日時 | 自動付与 | 自動付与 | 自動付与 | 必須 |

在庫数は、上表の項目に加えて第11章に定める手入力の項目を保持する。手入力の項目は取込では設定せず、再取込でも上書きしない。

在庫数量として保存するのは販売可能在庫だけである。実在庫数および引当済数は保存しない（[商品在庫取込要件 第4.5節](01.商品在庫取込要件.md)）。BOSSの`実在庫 (倉庫毎)`および`引当済 (倉庫毎)`は販売可能在庫の算出と入力値の検証にだけ使用する。

販売可能在庫は、全倉庫区分で「当該倉庫から現在出荷に充てられる数量」を表す。取込元によって算出方法は異なるが、値の意味は一致するため、倉庫区分をまたいで同じ指標として扱える。

## 6. 倉庫マスタ

倉庫区分ごとの属性を保持する。一意制約は`倉庫区分`とする。

倉庫マスタは在庫だけのマスタではない。[販売実績保存データ 第4.1節](../販売実績取込要件/04.販売実績保存データ.md)の出荷倉庫は、本マスタの倉庫区分と同一の値であり、販売実績と在庫の双方が本マスタを参照する。倉庫を追加する場合は、本マスタへの登録と併せて、販売実績側の出荷倉庫の変換規則も追加する。

| 保存項目 | 内容 | 必須 |
|---|---|---|
| 倉庫区分 | `BOSS自社倉庫`、`RFC`、`Amazon自社倉庫`または`FBA` | 必須 |
| 倉庫名 | 画面表示に使用する名称 | 必須 |
| 保管主体 | `自社`、`楽天`または`Amazon` | 必須 |
| 出荷対象モール | 当該倉庫から出荷するモールコード。複数を保持する | 必須 |
| 取得元 | 在庫の取込元レポート | 必須 |
| 補充元倉庫区分 | 当該倉庫を補充する倉庫区分 | 任意 |
| 在庫鮮度許容日数 | 在庫基準日からの経過日数の許容値 | 必須 |
| 有効・無効状態 | 当該倉庫を現在使用するか | 必須 |

初期の登録内容は次のとおりとする。

| 倉庫区分 | 保管主体 | 出荷対象モール | 取得元 |
|---|---|---|---|
| `BOSS自社倉庫` | 自社 | 楽天市場、Yahoo!ショッピング、au PAY マーケット | BOSS各在庫数レポート |
| `RFC` | 楽天 | 楽天市場、Yahoo!ショッピング、au PAY マーケット | BOSS各在庫数レポート |
| `Amazon自社倉庫` | 自社 | Amazon | Amazon出品詳細レポート |
| `FBA` | Amazon | Amazon | Amazon FBA在庫レポート |

補充元倉庫区分は、必要在庫数の算出で外部倉庫への補充を扱うために設ける（[在庫利用要件 第5章](06.在庫利用要件.md)）。実際の補充関係は未確定であるため、初期値を設定せず`NULL`とし、確定後に登録する。

## 7. 追加登録と再取込時の保存結果

在庫数は上書きせず、在庫基準日ごとに追加登録して蓄積する（[商品在庫取込要件 第4.4節](01.商品在庫取込要件.md)）。

- 一意キーが未登録の場合は、在庫数を新規作成する。
- 一意キーが登録済みの場合は、取込ファイルから再計算した保存項目で既存レコードを更新し、内部IDと作成日時は変更しない。
- 更新したレコードの更新日時と最終取込履歴IDを今回の取込に変更する。
- 在庫基準日が異なるレコードは、同一SKU・同一倉庫区分であっても別レコードとして追加する。過去の在庫基準日のレコードを更新も削除もしない。
- 今回のファイルに含まれないSKUの既存レコードは、削除も`0`への書き換えもしない。
- 直前の同一倉庫区分の取込に存在し、今回のファイルに存在しないSKUは、消失件数として取込履歴に記録し、警告する（[取込エラー・警告 第3章](08.取込エラー・警告.md)）。
- 未対応商品として在庫を登録しなかった行は、既存レコードの更新も行わない。
- 取得区分が`手入力`のレコードは、再取込で上書きしない（第11章）。
- 同じファイルを再取込しても、在庫数および倉庫別の合計を変化させない。

### 7.1 受入条件

| 操作 | 期待結果 |
|---|---|
| 新しい在庫基準日のBOSS各在庫数レポートを取り込む | 当該在庫基準日の`BOSS自社倉庫`と`RFC`の在庫数を新規登録し、過去の在庫基準日のレコードを変化させない |
| 同一在庫基準日の同一ファイルを再取込する | 在庫数および倉庫別の合計が変化せず、レコードが二重登録されない |
| 同一在庫基準日の訂正ファイルを再取込する | 既存レコードを更新し、最終取込履歴IDと更新日時が今回の取込に変わる |
| 前回取込に存在したSKUを含まないファイルを再取込する | 当該SKUの既存レコードを削除も`0`への書き換えもせず、消失件数と警告を記録する |
| 出品詳細レポートで`数量`が空欄のSKUを取り込む | `Amazon自社倉庫`の在庫数を登録せず、`0`としても登録しない |
| 手入力で登録した在庫数を含む倉庫区分・在庫基準日を再取込する | 手入力のレコードが保持され、取込値で上書きされず、警告を記録する |
| 商品コード対応表に存在しないAmazonのSKUを取り込む | 在庫数を登録せず、未対応商品件数と警告を記録する |

## 8. 最新在庫の特定

在庫試算の現在庫には、次のとおり在庫数を採用する。

- 倉庫区分ごとに、試算の基準日以前で最新の在庫基準日のレコードを採用する。
- 在庫基準の取込状態が`完了`でない場合も、取込が正常完了した倉庫区分の在庫は採用してよい。倉庫区分ごとに最新のレコードを独立して特定する。
- 倉庫区分によって採用した在庫基準日が異なる場合がある。採用した在庫基準日を倉庫区分ごとに保持し、画面に表示する。
- 試算の基準日と採用した在庫基準日の差が、倉庫マスタの在庫鮮度許容日数を超える倉庫区分は警告する。欠損として`0`を補わない。
- 在庫試算の版には、倉庫区分ごとに採用した在庫基準日と在庫数IDを保存する（[要件定義書 FR-070](../要件定義書.md)）。

## 9. 表示上の集計

倉庫別の合計値は保存せず、表示時に集計する（[商品在庫取込要件 第4.2節](01.商品在庫取込要件.md)）。

SKU1行に対して倉庫別の在庫数を横並びに表示する形式は、次のとおり在庫数から生成する。

| 表示列 | 生成元 |
|---|---|
| SKU | `在庫数.システム内商品コード` |
| BOSS自社倉庫在庫数 | 倉庫区分`BOSS自社倉庫`の販売可能在庫 |
| RFC倉庫在庫数 | 倉庫区分`RFC`の販売可能在庫 |
| Amazon自社倉庫在庫数 | 倉庫区分`Amazon自社倉庫`の販売可能在庫 |
| FBA倉庫在庫数 | 倉庫区分`FBA`の販売可能在庫 |
| 合計在庫数 | 上記4列の合計 |

```text
合計在庫数 = Σ(倉庫区分ごとの販売可能在庫)
```

- 当該SKU・当該倉庫区分の在庫数が存在しない場合は、`0`ではなく未取得として表示する。在庫が0であることと在庫のレコードが存在しないことを区別する。
- 未取得の倉庫区分がある場合、合計在庫数は実際の合計を下回る。合計値には未取得の倉庫区分があることを併記する。
- 各列に、採用した在庫基準日と在庫基準日からの経過日数を確認できるようにする。
- 合計在庫数は表示のための派生値であり、欠品判定および必要在庫数の算出には使用しない（[在庫利用要件](06.在庫利用要件.md)）。

## 10. 取込履歴

取込ごとに、少なくとも次の情報を保存する。

| 保存項目 | 内容 |
|---|---|
| 取込履歴ID | システムが付与する内部ID |
| 取込日時 | 取込を実行した日時 |
| 取込元 | BOSS各在庫数レポート、Amazon出品詳細レポート、Amazon FBA在庫レポートの別 |
| ファイル名 | 取り込んだファイルの名称 |
| ファイルの識別情報またはハッシュ値 | 同一ファイルの再取込を識別する値 |
| 在庫基準日 | 取込時に指定した在庫基準日 |
| ファイル内総行数 | 入力ファイルの行数 |
| 在庫対象行数 | 在庫として処理した行数 |
| 新規登録件数 | 新規作成した在庫数の件数 |
| 更新件数 | 既存レコードを更新した件数 |
| FBA出品除外件数 | 出品詳細レポートで`数量`が空欄のため取込対象外とした行数 |
| 販売不可在庫除外件数 | FBA在庫レポートで`Warehouse-Condition-code`が`SELLABLE`以外のため取込対象外とした行数 |
| 未対応商品件数 | 商品コード対応表に存在せず登録しなかった行数 |
| SKU識別レコード自動登録件数 | 商品属性未設定のSKU識別レコードとして自動登録した件数 |
| 消失件数 | 直前の同一倉庫区分の取込に存在し、今回のファイルに存在しなかったSKUの件数 |
| 手入力保持件数 | 手入力のため取込値で上書きしなかった件数 |
| 警告件数 | 記録した警告の件数 |
| エラー件数 | 記録したエラーの件数 |
| 処理結果 | 取込全体の処理結果 |

在庫数から最終取込履歴IDをたどることで、現在の値を登録または更新したファイル、取込日時および取込元を確認できるようにする。

## 11. 手入力による在庫の登録・修正

実地棚卸の結果の反映など、取込元データから取得できない在庫を担当者が手入力できる。 [要件定義書 FR-050](../要件定義書.md) の「在庫の取得元、取得日時および自動取得・手入力の区分を保持すること」に対応する。

手入力では、在庫数の取得区分を `手入力` とし、次の項目を追加で保持する。

| 保存項目    | 内容            | 必須                 |
| ------- | ------------- | ------------------ |
| 手入力メモ   | 担当者が任意に入力する補足 | 任意                 |
| 手入力者    | 最後に手入力を行った担当者 | 取得区分が `手入力` の場合は必須 |
| 手入力日時   | 最後に手入力を行った日時  | 取得区分が `手入力` の場合は必須 |

手入力の規則は次のとおりとする。

- 手入力で登録・修正したレコードは、取得区分を `手入力` に変更し、再取込で上書きしない。
- 手入力のレコードを含む倉庫区分・在庫基準日を再取込した場合は、確認用の警告を記録する（[取込エラー・警告 第3章](08.取込エラー・警告.md)）。
- 手入力のレコードを取込値に戻す操作は、担当者が取得区分を `自動取込` へ戻したうえで再取込することによる。自動では戻さない。
- 手入力値と自動取込値を画面上で識別できるようにする（[要件定義書 FR-071](../要件定義書.md)）。
- 過去の在庫基準日のレコードに対する手入力も許可する。ただし在庫数の変更履歴は保持し、変更前後の値、理由、変更者および変更日時を確認できるようにする。

在庫数の変更履歴の保存項目、および在庫試算の版との整合の取り方は未確定である。
